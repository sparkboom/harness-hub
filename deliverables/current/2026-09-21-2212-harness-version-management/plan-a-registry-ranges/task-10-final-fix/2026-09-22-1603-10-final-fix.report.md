## Finding 1 (Important) — `resolveHarnessStatus` crashes on unknown harness ids

**Problem.** `resolveHarnessStatus` passed `loadVersionsManifest()[harnessId]` (possibly
`undefined`) straight into `resolveVersion`, which dereferenced `entry.ranges` → `TypeError`.
Seam is consumed by `list`, `info`, and the doctor `versionStatus` rule.

**Fix.** `src/registry/resolve.ts` — `resolveVersion` now treats `entry == null` as one of its
existing unrecognized exits (early return of the shared `{ harnessId, installedVersion,
status: 'unrecognized', profile: null, range: null }` shape, hoisted into a local `unrecognized`
object so all four exits use one literal). The guard sits in `resolveVersion` itself (matching
the review's test guidance of calling `resolveVersion` with an undefined-cast entry), so the
exported `resolveHarnessStatus` seam is safe with no duplicated dead-path in that wrapper.

**Covering test.** `resolve.test.ts` "returns unrecognized instead of throwing when the manifest
has no entry for the id" — passes `undefined as unknown as HarnessVersionEntry` and asserts the
full unrecognized Resolution with `toEqual`. (With the shipped config all 8 ids exist, so the
missing-entry scenario is only reachable via this cast — same approach the review prescribed.)
Also added "resolves through the exported resolveHarnessStatus seam" exercising the real shipped
manifest via the exported function.

## Finding 2 (Important) — `parseVersion` wildcard guard rejected real banners containing `x`/`*` anywhere

**Problem.** The guard `/[xX*]/.test(cleaned)` ran on the whole string, so
`"codex-cli 0.155.1"` (real codex npm banner) failed to parse → installed in-range harnesses
reported unrecognized + spurious doctor warnings.

**Fix.** `src/registry/resolve.ts` — the wildcard test now applies only to bare wildcard range
specs: `/^v?\d+(\.\d+)*(\.[xX*]|[xX*])$/` matches `3.x`, `1.2.x`, `1x`, `v3.x`, `1*` (the final
wildcard component is optionally dot-prefixed). Everything else that fails `valid()` still falls
through to `coerce`, so banners (`"codex-cli 0.155.1"`) and prerelease x-components
(`"1.2.3-x"`, handled by `valid()`) keep parsing.

**Covering tests.** `resolve.test.ts`:
- "parses version banners with a package prefix" — `"codex-cli 0.155.1"` → coerces to 0.155.1 →
  resolves `unverified` in the open-ended codex range.
- "treats bare wildcard range specs as unparseable" — `3.x`, `1.2.x`, `v3.x` all unrecognized
  (keeps the pre-existing `3.x` → unrecognized pin passing).
- "still parses prerelease versions containing x-components" — `0.150.0-beta.1` → `verified`.

Note: an earlier guard draft (`{0,2}[xX*]$` without the dot) failed the new `3.x` test — the
dot before the wildcard component is part of the shape; fixed and re-verified.

## Finding 3 (Important) — loader didn't validate `min`/`max` as semver

**Problem.** A typo'd bound (`"0,155.0"`) passed loader validation and only blew up at
resolution time inside `gte`/`lt` (`TypeError: Invalid Version`) — a runtime crash instead of a
config-load error.

**Fix.** `src/registry/versions.ts` — imported `valid` from `semver`; extracted the per-range
bounds check into exported `assertValidRangeBounds(id, r)`, called from the loader's per-range
loop. Throws `config/config.json "<id>" has a range with an invalid semver bound (min|max "<value>")`,
style-matched to the existing loader error messages. Loader behavior preserved (throws at load).

**Covering tests.** `versions.test.ts` new `assertValidRangeBounds` describe: accepts good bounds
(min-only and min+max), throws with the exact message for bad `min` (`"0,155.0"`) and bad `max`.
