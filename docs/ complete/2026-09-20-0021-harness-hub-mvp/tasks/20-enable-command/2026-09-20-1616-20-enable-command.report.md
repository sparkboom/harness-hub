## Deviations

1. **Test 5 (`skill-migration collision`) and test 6 (`identical` migration): canon-side SKILL.md given valid frontmatter.**
   The fixtures wrote `.agents/skills/a/SKILL.md` with bare content (`two` / `same`). The merged `skill-frontmatter` rule is canon-wide and error-severity, so it fired (missing name/description) → the brief's own global-abort path returned `blocked` with ruleId `skill-frontmatter` before the intended harness-scoped findings could be observed. Fix: canon-side content is now `'---\nname: a\ndescription: x\n---\ntwo'` / `'---\nname: a\ndescription: x\n---\nsame'`, mirroring the merged `src/doctor/rules/skillFrontmatter.test.ts` fixtures. Semantics preserved: bodies still differ (`one` vs `two`) in test 5 → collision; both sides byte-identical in test 6 → identical. Note the harness-side content was left bare, which is fine: `skill-frontmatter` only scans canon (`.agents/skills`), and the collision/identical classification (`dirsByteIdentical`) is content-based.

2. **Test 10 (`blocks hermes when the repo is not trusted`): homeDir seeded with a config listing a different repo.**
   The fixture used a fresh empty homeDir. The merged `trustGate` rule emits severity `warning` ("Can't verify … does not exist") when `~/.hermes/config.yaml` is missing — asserted as such in its own merged test (`warns (does not error) when ~/.hermes/config.yaml is missing`) — so the verbatim test contradicted the merged rule: hermes was `enabled` instead of `blocked`. Fix: write `skills:\n  trusted_project_dirs:\n    - /some/other/repo\n` into `$homeDir/.hermes/config.yaml`, mirroring `trustGate.test.ts`'s "errors when the repo is not in trusted_project_dirs" case. This yields the definitive `hermes-trust` error, and the test now exercises the same trust-gate blocking path the plan intends.
