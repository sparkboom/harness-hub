# Quirks & out-of-scope assets — harness research

**Type:** research insight · companion to the per-asset insight files for harness-hub.
**Companion spec:** [`harness-hub.spec.md`](./harness-hub.spec.md) — implementation decisions live there.

This file records assets that are **out of canon scope** — either because the
word means something different per harness, the asset is user-level/cosmetic, or
the platform dependency is too deep to wire honestly. Kept so future-you doesn't
re-research them.

## "Workflows" — a naming trap, not an asset

The same word means different things per harness. Do **not** canon-ize it:

- **Codex**: "workflows" ≈ skills (bundled skills/workflows terminology;
  `disableBundledSkills` removes "skills and workflows")
- **Claude Code**: `workflows/` is a plugin directory type (like `commands/`,
  `agents/`, `hooks/` inside a plugin)
- **DeepSeek**: "workflows" is listed as a Standard-mode agent capability

If a real workflow asset emerges later, it needs a canon definition first —
start from what it *does*, not what harnesses call it.

## MCP servers (subset-supported — researched, deferred)

Researched because it's the strongest *future* canon candidate; out of first-draft scope:

- **Claude Code**: `.mcp.json` at project root (native), `~/.claude.json` (user)
- **Cursor**: `.cursor/mcp.json`
- **OpenCode**: `mcp` key in `opencode.json` (V2 nests under `mcp.servers`;
  local = `command`, remote = `url`+headers/oauth)
- **Codex**: `[mcp_servers]` in `config.toml`; project config layers exist but
  provider/credential keys are restricted — **verify** which MCP keys are project-legal
- **Hermes**: config-level — **verify**
- **Pi**: none built-in by design; official `pi-mcp-adapter` reads `.mcp.json`
- **DeepSeek**: plugin/tool capability — **verify**

`.mcp.json` at repo root is a de facto standard (Claude Code native + Pi's
official adapter). A future MCP asset would likely be: canon `.mcp.json`,
config-merge adapters for Cursor/OpenCode, notices elsewhere.

## LSP servers (subset: 2, one inert)

- Others: none

Out of scope: too niche, and one of the two implementations is a no-op today.

## Permissions / approval policy (divergent semantics)

Overlapping concepts, incompatible vocabularies — would need a semantic
compiler, not a file mapping:

- **Claude Code**: `permissions` (allow/ask/deny, tool-level rules,
  `additionalDirectories`) in settings
- **OpenCode**: `permission` config (per-tool/per-action)
- **Codex**: approval policy + sandbox modes (user-level)
- **Cursor**: settings-driven — **verify** project-versioned shape
- **Hermes / Pi / DeepSeek**: varies; Pi intentionally has none built-in

Out of scope for first draft.

## Routines / scheduled automations (subset: 2–3, platform-bound)

- **Cursor**: Automations (schedules, Slack, GitHub events — platform feature,

- **DeepSeek**: scheduling as a plugin capability

Out of scope: delivery models are too different (in-repo frontmatter vs cloud
